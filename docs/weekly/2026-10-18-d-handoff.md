## 3. 真实实验结果，应该怎样解释

| 示例 | 轮次 | 模型策略 | 真实 token | 实际观察 |
| --- | --- | --- | --- | --- |
| popcount3 | 1 | area_simplify | 448 | 只删除原始注释，没有实质逻辑修改 |
| addsubz | 1 | area_simplify | 541 | 返回原始代码，没有实质逻辑修改 |
| addsubz | 2 | timing_restructure | 714 | 收到模拟时序反馈后改写表达式，尚未验证或测量 |

本阶段 3 次 RTL 生成合计 **1703 token**，调用计时合计约 **5.13 秒**；不包含此前 10 token 的短文本连通性检查。
模型为 deepseek-v4-pro；生成 is_mock=false。只有第三次反馈的 feedback_is_mock=true，表示输入反馈是人工模拟，不代表该候选实际违反了时序约束。

addsubz 第二轮把条件加减改成了对 b 做条件补码后相加的写法。这只说明模型按反馈生成了另一种 RTL 表达，并不能说明综合后更小或更快。
所有轮次从各自原始 RTL 生成，未把未经验证的候选当作可信基线。此演示是 D 的连续反馈机制检查，不是 A/B/C 的完整闭环。

实验中发现旧版文本去重不能识别“只删除注释”，因此本次增加 token 指纹，并对已生成结果做了离线复核。原始调用记录与事后审计分别保留，避免混淆。

## 5. 组会上建议演示什么（约 5 分钟）

1. 打开 [D 运行说明](../optimization.md)，展示函数和命令行入口。
2. 打开 [精选实验](../../experiments/demo_2026-10-17/README.md)，展示原始 RTL、两轮 addsubz 候选与实际反馈文件。
3. 打开 evidence.json，指出三次实际用量、run_id 和“没有验证/评估”的标记。
4. 展示模拟时序反馈对应 timing_restructure；强调模拟的是反馈，候选确实来自真实 API。
5. 用 mock 运行一次保存流程，避免会议现场依赖网络、余额或再次付费。

从项目根目录运行（Python 3.10+，标准库即可）：

```bash
# 可使用已收录的源码快照，无需另行下载 Demo，无 API 消耗
python -m src.optimization experiments/demo_2026-10-17/addsubz_original.v --backend mock --context experiments/demo_2026-10-17/addsubz_context.json --history runs/meeting/history.jsonl

# 需要 tmp/opti_demo；3 轮均为 mock，含模拟反馈
python -m src.optimization.demo --backend mock

# 回归测试
python -m unittest discover -s tests -p test_optimization.py -v
```

完整真实生成复现入口为 `python -m src.optimization.demo --backend custom`，最多 3 次 API 请求，有费用且输出不保证完全一致。

## 6. 具体交给队友什么

### 给 A：调用接口与结果处理

```python
from src.optimization import optimize

result = optimize(
    current_rtl, feedback,
    context={"design_id": "case_id", "top": "TopModule", "parameters": {},
             "constraints": {"delay_limit": None, "delay_unit": None}},
    history_path="runs/case_id/history.jsonl",
)
```

- 原有两个位置参数仍可使用；context 与 history_path 可选。
- status=success 只表示候选已保存。is_duplicate=true 可跳过重复评估，由 A 决定继续、换策略或停止。
- is_mock 是生成后端标记；feedback_is_mock 是反馈来源标记。模拟反馈不能作为真实验证或评估依据。
- 返回 candidate_path、strategy、run_id、record_path、prompt_path、usage、耗时等信息。
- 同一个 design_id/context 的历史文件应串行写入；参数或约束变化会隔离历史。未知约束填 null，不虚构数值。
- A 保留原始 golden、调用 B/C、选择最佳有效版本并管理正式循环；D 演示脚本不接管这些职责。

### 给 B：原始 RTL 与待验证候选

先检查精选实验中的 `addsubz_original.v` 与 `addsubz_r2.v`，顶层为 TopModule。
返回 equivalent、status、error_type、error_log，保留真实验证方式和日志。
后续 D 会接收不等价反馈生成修复候选；目前只测过这条策略的模拟分支，没有真实修复成功结论。

### 给 C：验证通过后再测量

B 确认通过后，按同一配置测原始与候选，返回 area、delay、单位、timing_met 和报告路径。
组会需确认库版本、延时定义与约束；逻辑深度不能直接当作纳秒延时。
本次没有面积或延时数据，也没有可报告的优化百分比。
